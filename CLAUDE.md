# CLAUDE.md — halogen-stack

Рабочий документ проекта. Инструкции среды для агента — в `/docs/CLAUDE.md`
(он приоритетнее этого файла в вопросах запуска контейнера, сети, прав на запись).

## 1. Цели проекта

1. Безопасный запуск `halogen-flash-server` (LLM-инференс-сервер).
2. Обратный прокси перед `halogen-flash-server` — изолировать от прямых запросов.
3. Персональные ключи пользователей (поддержка 4 пользователей).
4. Запуск WebUI (Open WebUI).
5. Изоляция всех приложений от хостовой машины.
6. Изоляция приложений от интернета: приложения не исходят наружу; WebUI —
   только GET на разрешённые сайты.

**Статус: цели и план ещё согласованы не полностью.** Не начинать реализацию
без явного «go» по текущему этапу.

### 1.1 Список сервисов (зафиксирован 2026-10-25)

Основные:

| # | Сервис | Роль |
|---|---|---|
| 1 | halogen-flash-server | LLM-инференс |
| 2 | web-ui | Open WebUI |
| 3 | internal-auth-provider | владеет всеми ключами пользователей |
| 4 | reverse-proxy | единственная точка входа к LLM API |
| 5 | waf-firewall | фильтрация входящего трафика |
| 6 | egress-proxy | squid: единственный маршрут web-ui наружу (whitelist + GET) |

На будущее (возможно, на отдельном сервере мониторинга): metrics-waf,
node-exporter, blackbox-exporter, prometheus, grafana.

### 1.2 Зафиксированные решения (2026-10-25)

- Все ключи пользователей — у `internal-auth-provider`.
- Редактирование ACL — конфигурационными файлами; UI не нужен, но процесс
  подробно документируется.
- WebUI разрешено чтение документации (пример: php.net); видео, картинки и
  прочий медиа-контент запрещён.
- GPU-проброс принят как ограничение изоляции от хоста.
- Проверенный `compose.yaml` — **не эталон**; любые отклонения требуют тестов
  на сервере пользователя.
- `internal-auth-provider` — **своя минимальная реализация**. Ключи хранятся на
  хостовой машине, монтируются в контейнер auth-provider. Обновление ключей,
  ACL и whitelist WebUI — через `make` администратором сервера (вне контейнера).
- Модель пользователей (4 ключа auth-provider):
  - 3 ключа — агенты с 2 ноутбуков в **локальной сети** (прямой API-доступ);
  - 1 ключ — сервисный, для `web-ui` (живёт в internal-сети).
- Учётные записи Open WebUI — для **внешних** пользователей, в т.ч. из
  интернета. auth-provider их не касается: WebUI ходит в LLM одним сервисным
  ключом.
- LLM API доступен **только через reverse-proxy** с проверкой ключа через
  auth-provider (forward-auth, подтверждено). `halogen-flash-server` и
  `internal-auth-provider` не имеют портов на хосте: из интернета и напрямую
  недоступны.
- Публичный вход: `https://ai.dda2543.ru` → `waf-firewall` (TLS-терминация +
  CRS). Сертификат — certbot на хосте через `make`. **DNS-запись ai.dda2543.ru
  ещё не создана** — предпосылка публичного запуска.
- Scope WAF — только публичный путь WebUI (LAN-путь агентов без WAF).
- Каркас фазы 2 (создан 2026-10-26, **на сервере не проверялся**):
  `compose.public.yaml` (waf-firewall в сети `public`, порт хоста `443`→`8443`
  в контейнере — без `CAP_NET_BIND_SERVICE`), `waf/Dockerfile` (Caddy+Coraza+CRS,
  версии ARG — зафиксировать после первой сборки), `config/caddy/Caddyfile.waf`
  (`SecRuleEngine DetectionOnly` на первый прогон), `make waf-build/public-up/
  cert/cert-renew`, `docs/admin-public.md`, чек-лист §Е. Два решения: сертификат
  через `certbot --standalone` (waf занимает только 443; редиректа HTTP→HTTPS
  нет), и reverse-proxy отвечает `403` на `/v1/*` с публичным `Host` — LLM API
  наружу не светится. Предпосылка на хосте: `net.ipv4.ip_unprivileged_port_start=0`.
- Механизм auth-provider (подтверждён): reverse-proxy → forward-auth к
  auth-provider на каждый запрос; ключи в файлах хоста, перечитывание по
  сигналу/таймеру.
- Путь агентов (решение 2026-10-26, заменило «HTTP в LAN» и «self-signed TLS»):
  **WireGuard на сервере + VLAN-containment на роутере**. `8731` биндится на
  туннельный адрес (`LAN_IP=10.80.0.1`), в LAN слушателя нет; из интернета
  проброшены только 443 и 80 (ACME). Два слоя ключей (пир WG + `keys.acl`) —
  осознанно. Документация: `docs/admin-router-mikrotik.md`,
  `docs/admin-server-ubuntu.md`, `docs/admin-client-macos.md`; канон —
  `docs/architecture.md` §3.1. Реализация — вне репозитория (роутер и хост),
  агент к ней не причастен.
- Whitelist доменов WebUI: **изначально пуст**; в документации — пример
  добавления php.net.
- web-ui запускается с `OFFLINE_MODE: "true"` (решение 2026-10-26): эмбеддинги с
  HuggingFace не скачиваются (их всё равно режет egress), проверка версий
  выключена. **Уточнение 2026-10-28: RAG-встраивания на этом сервере работают** —
  прежняя формулировка «не работают» была неверна. `all-MiniLM-L6-v2` уже лежит в
  томе `webui_data` (`/app/backend/data/cache/embedding/models/…`) и грузится
  локально, лог чистый. Вероятный источник: модель скачалась в первую загрузку,
  пока у web-ui не был закрыт прямой путь наружу через сеть `egress` (дефект,
  исправленный в сессии 1 введением `wan`); том пережил и рестарты, и
  `OFFLINE_MODE`. Это незадокументированная зависимость: при пересоздании тома
  модель не восстановить — egress её не пропустит. Если RAG нужен всерьёз —
  вынести кэш HF в отдельный том (дорожная карта).
- `egress-proxy` (squid) **одобрен** как 6-й сервис: единственный контейнер
  с маршрутом наружу; web-ui ходит через него по `HTTP_PROXY`.
- ПО прокси **одобрено — Caddy дважды**: `waf-firewall` = Caddy+Coraza (CRS),
  `reverse-proxy` = чистый Caddy с `forward_auth` к auth-provider.
- MVP: `halogen-flash-server` запускается **без** `HALOGEN_API_KEY` (не
  тестирован на сервере). Защита LLM API — только сетевая изоляция (доступен
  лишь с reverse-proxy). Включение ключа — roadmap (§9).
- Prompt-кэш halogen — **только в RAM** (решение 2026-10-28, ветка
  `agent/prompt-cache-ram-only`): `HALOGEN_CACHE_DIR` не задан, том `/cache`
  не монтируется, `HALOGEN_FORK: "0"`. Причина: дисковый слой разросся до
  42 GiB за 14 минут работы Claude Code (28 разговоров × ~1.4 GiB) при
  33 GiB свободного места на разделе; лимит `HALOGEN_CACHE_DISK_GIB=64` был
  больше свободного места, поэтому LRU-чистка не включалась никогда. Цена:
  после рестарта контейнера все разговоры холодные — на реальных сессиях
  Claude Code (123–128k токенов) это 2–2.5 минуты prefill, а не 40 с на 32k.
  Возврат — раскомментировать две переменные в `compose.yaml` и вернуть том
  `/cache`, лимит взять заметно меньше свободного места раздела.
- **Образ `halogen-flash-server` поднят 0.18.15 → 0.20.0** (решение человека от
  2026-11-08, пин в `compose.yaml`). Между ними пять релизов; на нас влияют:
  0.18.16 — auto-keep выключен по умолчанию (причина нашего `HALOGEN_FORK=0`
  изменилась, сам `0` оставлен как явный и как отказ от именованных keep-состояний);
  0.18.18 — Claude Code с tool-search больше не сбрасывает prompt-кэш;
  0.18.19 — `/v1/messages` при переполнении контекста отдаёт штатную строку
  Anthropic (её Claude Code умеет compact + retry), снят лимит «не больше 64
  картинки»; 0.19.0 — API-порт слушает IPv6 вдобавок к IPv4; 0.19.1 — битая
  tool-схема даёт `400` и освобождает слот (до этого `500` + утерянный слот:
  несколько таких запросов останавливали генерацию); 0.20.0 — образ на ROCm 10.1
  (−9…15% энергии при генерации при той же скорости) и фикс краха движка при
  конкурентных strict tool calls. Ответы могут отличаться от 0.18.15 в последних
  битах — это заявлено апстримом. NPU-новости (LFM3, d1-2B, OvisOCR3) и
  опциональный `HALOGEN_AGENT_GUARD` в стек не встроены: драйвер NPU появился на
  хосте в тот же день, но цели для него не выбраны и «go» не давалось (§5, §9).
  **На сервере 0.20.0 поднят 2026-11-08**: версия front end и движка 0.20.0,
  слушает `[::]` и `0.0.0.0:8731`, warm start 0.29 с — старт чистый. Остальное
  из §A1 чек-листа (скорость, RAM-only, доля кэша, `400` на битую схему) ещё не
  проверено.
- `/healthz` **закрыт наружу** (решение 2026-10-28): матчер `@public_halogen` в
  `config/caddy/Caddyfile` отдаёт `403` на `/v1*` **и** `/healthz` при публичном
  `Host` — раньше публично читалась версия движка. С LAN-пути `/healthz`
  по-прежнему 200 (диагностика). **Проверено на сервере 2026-10-28** подстановкой
  публичного `Host` на LAN-порту прокси: `-H 'Host: ai.dda2543.ru'` → `403`,
  без заголовка → `200`. Отдельный `caddy validate` по этому матчеру не нужен —
  конфиг разобран живым Caddy. Сквозная проверка снаружи — после открытия WAN.
- Публичный вход **пока недоступен из интернета**: запись DNS `ai.dda2543.ru` →
  `95.31.220.107` есть, но входящие порты на WAN роутера закрыты (§6.9).
  `make waf-build` от этого не зависит и прогоняется; `make cert` в режиме
  `--standalone` — нет.
- Оба проброса на хосте параметризованы и не могут раскрыться молча
  (изменение 2026-10-28). `LAN_IP`: раньше `"${LAN_IP}:8731:8080"` при пустой
  переменной давал `":8731:8080"` = публикацию на всех адресах; теперь страховки
  две. `GUARD_LAN_IP` в `Makefile` (`make up`/`public-up` падают до всякой
  интерполяции, внятное сообщение) — логику прогнана в контейнере агента на `sh`
  на пяти записях: пусто/пробелы в `.env`, `.env` отсутствует, значение из `.env`,
  значение из окружения, окружение с пустым значением. И `${LAN_IP:?…}` прямо в
  `compose.yaml` — она закрывает **запуск в обход make** (прямой вызов
  `podman-compose`), решение человека от 2026-10-28; падает трейсбеком
  `RuntimeError`, но громко.
  Порт 443 у waf —
  `${PUBLIC_BIND_IP:-0.0.0.0}:443:8443`: пусто = прежнее поведение каркаса, после
  VLAN в `.env` ставят адрес WAN-интерфейса, и из LAN в 443 напрямую не попасть.
  Значение `PUBLIC_BIND_IP` на сервере ещё не выставлено (адрес WAN не закреплён
  до VLAN), сами guard'ы `make up` ещё не прогонялись.
- **MAC (SELinux/AppArmor) в план не входит** (решение 2026-10-28): изоляция стека
  держится не на нём — сети podman (три `internal`, `wan` только у squid), ровно
  два проброса на хост, `read_only` + `cap_drop: ALL` + `no-new-privileges` +
  tmpfs, и rootless podman (uid 0 контейнера = uid администратора, не root).
  MAC ограничил бы только два принятых ограничения — `ipc: host` и GPU-проброс,
  а его цена на этом хосте (смена дистрибутива либо `enforcing` на живом хосте с
  переразметкой всех томов, включая 111 GiB моделей) не окупается. Дешевле
  AppArmor, но применимость под вопросом: в rootless podman навешивание профиля
  на контейнер — привилегированная операция (на сервере не проверялось; смотреть
  `sudo aa-status` и `podman info -f json` → `.Host.Security.apparmorEnabled`).
  Повод вернуться: публичный вход включён и `ipc: host` остаётся надолго
  (провал эксперимента §D).

## 2. Режим работы

- Планируем и обсуждаем до правок. Ищем противоречия, фиксируем их здесь.
- Маленькие подзадачи: минимальный результат → правки. Не брать всё сразу.
- Лимит рассуждения/ответа агента — 12k токенов, думать поэтапно.
- `git push` — только человек. `git commit` — **разрешён агенту** решением
  пользователя от 2026-10-25 (чекпоинты ради чистого diff и отката).
  Ограничения: не переписывать историю (amend/rebase/reset на закоммиченном),
  коммитить только осмысленные вехи, сообщение коммита — на русском.

## 3. Среда разработки (контейнер агента)

- Режим: **dev** (`/workspace/src` — rw). Podman 5.7.0 на хосте пользователя.
- Сеть контейнера агента: internal-сеть, наружу только через HTTP-прокси
  `http://proxy:3128`. Это же — эталон паттерна изоляции для halogen-stack.
- Маршрута к LLM из shell'а агента нет: TCP до `192.168.101.249:8731` →
  `ENETUNREACH` (проверено 2026-11-08); рантайм Claude Code ходит в движок сам,
  минуя песочницу. Следствие для планирования: инструменты агента (grep, read,
  под-агенты) не могут вызвать `POST /v1/embeddings` или `/v1/rerank` — векторный
  поиск по репозиторию не откроется даже с включённым NPU.
- Секреты (`.env`, токены) агенту недоступны намеренно.
- При сетевой ошибке — остановиться и сообщить человеку, не искать обходы.
- Инструменты в контейнере агента (проверено 2026-10-25): **node v24** — основной
  скриптовый инструмент (текстовые/файловые операции делать на нём), есть также
  `perl` и `git`. **Нет `python3`, `jq`, `yq`, `make`, `curl`, `wget`, `podman`** —
  не пробовать, сразу node.
- `podman` и `make` — на сервере пользователя, не у агента: compose/Makefile
  здесь пишутся, но выполняются и тестируются человеком на сервере.
- **Журнал памяти агента здесь недоступен**: `/home/agent` read-only, каталог
  `~/.claude/projects/-workspace-src/memory/` создать не выходит (проверено
  2026-10-28). Всё, что «сохранить на потом», идёт только в этот файл и в
  `docs/` — отдельного хранилища фактов у агента нет.
- Git в контейнере: `GIT_CONFIG_GLOBAL=/tmp/gitconfig` и
  `-c safe.directory=/workspace/src`; `chmod` запрещён. Наружу из контейнера
  только `HTTP_PROXY`, поэтому `git fetch`/`ls-remote` не работают (remote по
  SSH, `ssh` в образе отсутствует) — `origin/*` виден на момент последнего
  fetch, который делает человек.

## 5. Установленные технические факты

- `halogen-flash-server` — OpenAI-совместимый API + Anthropic-совместимый вход
  (`x-api-key`), слушает порт **8731** (по умолчанию; env `HALOGEN_API_PORT`).
  Требует GPU-устройства хоста: `/dev/kfd`, `/dev/dri`, `ipc: host`, `memlock=-1`,
  группы video/render (`group_add: keep-groups`). Источник:
  `/docs/halogen-flash-server/docs/api.md:3`, `deploy/entrypoint.sh:27`
  (`API_PORT=${HALOGEN_API_PORT:-8731}`). Внимание: в проверенном `/docs/compose.yaml`
  стоит проброс `"8731:8000"`, но там `network_mode: host` — он игнорируется,
  приложение слушает 8731 (отсюда ошибочные «8000» в ранних версиях этого дока).
- **Аутентификация: ровно один ключ** `HALOGEN_API_KEY` (или `HALOGEN_API_KEY_FILE`).
  Без ключа — 401 на всех маршрутах кроме открытого `/health`.
  Источник: `docs/configuration.md:498+`, `docs/api.md:15`.
  ⇒ **Персональные ключи 4 пользователей возможны только на обратном прокси**
  (N пользовательских ключей → один upstream-ключ).
- Проверенный compose: `network_mode: host`, `read_only: true`, tmpfs `/tmp`/`/run`,
  `cap_drop: ALL` + `NET_BIND_SERVICE`/`NET_RAW`, модели `~/halogen-models:/models:ro`,
  кэш `./cache:/cache:z`. Источник: `/docs/compose.yaml`.
- **SELinux на сервере нет** (проверено 2026-10-28: `dpkg -l | grep selinux` →
  только `libselinux1`, а это рантайм-библиотека-зависимость; Ubuntu по
  умолчанию на AppArmor. Подтверждено напрямую: `[ -e /sys/fs/selinux ]` →
  «SELinux выключен»). Ранешняя формулировка «SELinux-enforcing хост» была
  выведена неверно — из флага `:z` в проверенном `reference/compose.yaml`.
  Флаги `,z`/`:z` в монтированиях оставлены намеренно: на хосте без SELinux это
  no-op, но они нужны при переносе. Пункт чек-листа про `ausearch -m avc` убран.
- **`halogen-flash-server` — FastAPI/uvicorn** (в логе 0.18.15 — `Uvicorn running
  on http://0.0.0.0:8731`, предупреждение `@app.on_event("startup")`), в access-логе
  печатает полный request-target вместе с query (`"GET /v1/model?x=1" 404`).
  404 в таком случае — от неизвестного пути, а не из-за query. Query на валидном
  пути (`/v1/models?x=1`) на сервере ещё не проверялся. Источник: логи сервера,
  сессия 3. **С 0.19.0 uvicorn запускается с `--host ::`**
  (`/docs/halogen-flash-server/deploy/entrypoint.sh:1091`) — слушает IPv4 и IPv6.
  **Подтверждено на сервере 2026-11-08** на 0.20.0: лог старта даёт
  `serve_api: engine at 127.0.0.1:8730, listening on [::] and 0.0.0.0:8731` плюс
  `Uvicorn running on http://[::]:8731` — то есть front end слушает оба стека, а
  сам движок живёт только на loopback `127.0.0.1:8730` и из podman-сети недоступен
  (полезно: единственная точка входа в контейнер — 8731). Предупреждения
  `on_event` в 0.20.0 правда нет. Рядом печатается warm start 0.18.23 — у нас
  `warm start: one 15-token request, 10 tokens, 0.29 s, before listening`, то
  есть первая инициализация движка уже не внутри первого клиентского запроса.
  Версию всё равно читать из `/health` — он отдаёт версию front end и движка
  (`/docs/halogen-flash-server/docs/api.md:69`), у нас этот маршрут торчит как
  `/healthz`.
- **Caddy `forward_auth` сохраняет query-строку исходного запроса.** Он реализован
  как `reverse_proxy` + `rewrite` на `uri`; `RawQuery` перезаписывается только если
  в самом `uri` есть `?` (`/docs/caddy/modules/caddyhttp/rewrite/rewrite.go:274`).
  Значит `POST /v1/messages?x=1` приходит на auth-provider как `GET /authz?x=1`.
  Лечится: `uri /authz?` (пустой `?` гасит query) + сравнение только пути в
  auth-provider.
- **`podman-compose` реализует `${VAR:?сообщение}` как `raise RuntimeError`**
  (`podman_compose.py:306`, `raise RuntimeError(m.group("err"))`): при заданном
  значении подставляет его, сообщение съедается; при пустом/отсутствующем —
  падает необработанным трейсбеком вместо внятной ошибки. Всё после `}` — часть
  значения, поэтому суффикс порта обязан быть внутри (`"${VAR:?…}:8731:8080"`).
  Два факта про источник значения, оба проверены 2026-10-28: **GNU make
  экспортирует команднострочные `VAR=` в окружение рецептов** (`LAN_IP= make up`
  доходит до podman-compose) и **пустое значение из окружения перебивает
  валидный `.env`** — именно поэтому `LAN_IP= make up` падал с `RuntimeError`,
  хотя в `.env` значение было. Ранняя версия этого дока утверждала обратное по
  неверной расшифровке прогона.
- **Матчер `path` в Caddy видит только `r.URL.Path`, query игнорирует**
  (`/docs/caddy/modules/caddyhttp/matchers.go:439`). `/v1/*` — это prefix-матч по
  `/v1/` (`matchers.go:521`), поэтому голый `/v1` не матчится и проваливается в
  соседний `handle` (к web-ui).
- **rootless podman (на сервере):** uid 0 в контейнере = uid администратора
  хоста. Поэтому `internal-auth-provider` читает host-`keys.acl` (0600) через
  `user: "0:0"` в compose — без chown и без флага монтирования `U` (U
  переставлял владельца на подuid). Источник: `compose.yaml`
  (internal-auth-provider) + маппинг uid в rootless podman.
- **Образ `halogen-flash-server` включает fork-механизм сам.** Если переменная
  не задана, entrypoint экспортирует `HALOGEN_FORK=1`
  (`/docs/halogen-flash-server/deploy/entrypoint.sh:1014`). Auto-keep
  (`HALOGEN_FORK_MAP=auto`) был дефолтом **только в 0.18.15** (`FLAGS.md:161`) и с
  0.18.16 выключен самим апстримом (#207, #208) — прежняя формулировка этого дока
  «entrypoint подставляет и `FORK_MAP=auto`» верна лишь для 0.18.15; в 0.20.0 в
  entrypoint только `HALOGEN_FORK`. Auto-keep хранит состояние конца каждого
  ответа (~0.1 GiB RAM + позиции KV-пула, `FLAGS.md:160`), а с `HALOGEN_CACHE_DIR`
  ещё и пишет его на диск. Справочный `sessions.md` здесь устарел: утверждает
  «off by default», тогда как `FLAGS.md:157` — «on by default since 0.18.15».
  Отключается только явным `HALOGEN_FORK=0`; при `0` entrypoint `FORK_MAP` не
  подставляет, так что «map без HALOGEN_FORK=1» (останавливает сервер) не
  происходит. Наш явный `0` оставлен и после апгрейда: при `1` живы именованные
  keep-состояния по заголовку `X-Halogen-Keep`, а их имена — общее пространство
  для всех ключей сервера (`FLAGS.md:157`); Claude Code эти заголовки не шлёт.
- **Дисковый prompt-кэш halogen: ~27 KiB на токен контекста** — 0.9 GB при 32k,
  2.7 GB при 100k, 7.2 GB при 262k
  (`/docs/halogen-flash-server/docs/configuration.md:344-345`, `FLAGS.md:134`).
  Один разговор поэтому ограничен ~7.2 GiB при `HALOGEN_CTX=262144` — растут не
  отдельные разговоры, а их *количество* (у Claude Code: основной тред, каждый
  субагент, side-запросы title/summary) и число поддеревьев конфигураций.
  `HALOGEN_CACHE_DISK_GIB` ограничивает только текущее поддерево и вытесняет по
  LRU лишь когда новый разговор превысит лимит (`FLAGS.md:135-136`).
  Поддерево = сборка + веса + контекст + числовые настройки; `fingerprint`
  внутри него перечисляет эффективные env (так и выяснилось, что `HALOGEN_FORK=1`
  ставит образ). `handles.json` и `fingerprint` документацией не описаны.
- **На сервере есть NPU (XDNA), в стек он не включён** (сообщено человеком
  2026-11-08): `lsmod | grep amdxdna` → `amdxdna` + `amd_pmf`, узел
  `/dev/accel/accel0` (`crw-rw-rw- root:render`, 261:0), драйвер собран из
  исходников в `~/xdna-driver/build`, версия `2.27.0_20261108` — новее пары
  «DKMS 2.23 + его XRT 2.23», которую апстрим помечает как заведомо плохую
  (`/docs/halogen-flash-server/docs/NPU.md:948`); XRT 2.25.37 образ 0.20.0 носит
  сам и монтировать хостовой не нужно (`NPU.md:942`).
  **Что потребуется, если включаем** (реализации ещё нет, решения человека нет):
  (1) `--device /dev/accel/accel0` — третий проброс хостового устройства после
  `/dev/kfd` и `/dev/dri`, то есть ещё одно принятое ограничение изоляции (§1.2);
  (2) **зафиксированная fabric-частота GPU** — на Strix Halo GPU и NPU вместе
  могут вешать машину и портить результат NPU, пока частота меняется, из rootless
  контейнера её не зафиксировать, нужен хостовый systemd-юнит
  `halogen-fabric-clock`, и апстрим прямо говорит, что на части хостов hard hangs
  остаются даже с ней (`NPU.md:38-40`, ROCm/TheRock#8709, правку ждут в BIOS);
  (3) `HALOGEN_DOWNLOAD` **не используем** — он качает веса/NPU-программы на
  первом старте и требует rw `/models` и маршрут наружу, а у halogen нет ни того
  ни другого; файлы NPU-моделей человек кладёт в `~/halogen-models/npu/` руками,
  и тогда конвертация «своих» чекпойнтов повторяется на каждый старт
  (`NPU.md:611`); (4) NPU-модели держат незакачиваемую хостовую память
  0.8–7.6 GiB на модель сверх весов Flash и KV-пула, порог
  `HALOGEN_NPU_HOST_FLOOR_GIB=4` (`NPU.md:60-64`) — объём RAM сервера под это
  ещё не считали.

## 6. Обнаруженные противоречия (к разрешению на этапе планирования)

1. **Host network vs изоляция.** Проверенный compose использует `network_mode: host`
   (и `ipc: host` для ROCm shared memory). Цели 5–6 требуют internal-сетей.
   Нужно проверить, живёт ли `ipc: host` с podman-сетями (скорее да: ipc и сеть
   независимы), и чем заменить `NET_RAW`/`NET_BIND_SERVICE`.
2. ~~Один ключ сервера vs 4 пользователя~~ — **решено**: reverse-proxy Caddy +
   forward-auth к auth-provider (§1.2).
3. **WebUI наружу только GET на разрешённые сайты.** «Только документация» —
   семантически нефильтруемо; технический компромисс: egress-прокси (squid-подобный)
   с whitelist доменов + метод GET + allowlist Content-Type (text/html,
   text/plain). Медиа отсекается по Content-Type, но это эвристика. Требует
   конкретного списка доменов (§7.6). Также: сборка образа Open WebUI требует
   pypi/npm на build-time — это отдельный сетевой контекст, не runtime.
4. ~~GPU~~ — **принято как ограничение** (см. §1.2).
5. ~~Обратный прокси: какой?~~ — **решено**: Caddy (§1.2).
6. ~~Имя сервиса №1~~ — **разрешено**: сервис №1 = `halogen-flash-server`.
8. ~~Нет egress-фильтра для WebUI~~ — **решено**: `egress-proxy` (squid)
   одобрен как 6-й сервис (§1.2).
7. **`ipc: host` в проверенном compose** делит IPC-namespace хоста — против
   цели 5. Проверить на сервере: ROCm с приватным IPC + `shm_size` вместо
   `ipc: host`; заодно — нужна ли ещё `NET_RAW`. **Но: upstream утверждает, что
   этот тест заведомо обречён** — `/docs/halogen-flash-server/docker-compose.yml:118-120`:
   `ipc: host` load-bearing, «no `shm_size` substitutes (five sizes from 64 MiB
   to 64 GiB fail identically)», нужна именно общая namespace. Прежде чем
   тратить прогоны, решить, принимаем ли мы `ipc: host` как второе ограничение
   изоляции (первое — GPU-проброс, §1.2).
8. ~~**SELinux vs Ubuntu**~~ — **закрыто 2026-10-28**: SELinux на сервере нет
   (в `dpkg` только `libselinux1`, хост на AppArmor). Флаги `,z`/`:z` оставлены
   как безвредные, пункт чек-листа про `ausearch -m avc` убран. Факт — в §5.
9. **Публичный вход упирается в роутер, а не в DNS.** DNS `ai.dda2543.ru` уже
   указывает на `95.31.220.107`, но входящие порты на WAN роутера закрыты, и
   **открыть их планируется только после VLAN и WG** (решение человека от
   2026-10-28). Следствие: до этого `make cert` в режиме `certbot --standalone`
   (HTTP-01) не пройдёт проверку — Let's Encrypt не достучится до :80, — и
   чек-лист §Е целиком непроверяем. Порядок «сначала сегментация, потом WAN,
   потом сертификат» остаётся рабочим; DNS-01 нужен только если сертификат
   понадобится раньше WAN. Порядок — в точке входа, пункты 3–5.

**Развязка (тот же вечер, конец смены).** Источник значения — `.env`:

обнулили вручную, а после теста вернули. То есть обе ветки проверки сработали как
надо: обнулённый `.env` → сообщение Makefile-guard'а, пустая переменная
окружения поверх валидного `.env` → `RuntimeError` из compose. Из этого же
следует опровержение моей прошлой записи: **make команднострочные `VAR=` в

оставляем** — `${LAN_IP:?…}:8731:8080` возвращена в `compose.yaml`.
